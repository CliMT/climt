# climt Website Design

**Date:** 2026-05-18
**Status:** Draft — awaiting user review
**Author:** Joy Monteiro (with Claude)

## Goal

Replace the existing Sphinx documentation with a single Quarto-based GitHub Pages site that unifies (a) the existing user/API documentation, (b) a graduate-level radiative-transfer textbook walkthrough, (c) a formal blog of long-form experiment writeups (cork saga first), and (d) runnable Jupyter notebooks. The site is the public face of climt; it should serve students learning radiative transfer, practising climt users, and contributors extending climt to other planets — without forcing each reader to read everything.

## Audience

Layered per page, surfaced through Quarto callouts rather than parallel sections:

- **Practitioner** — climt user debugging or configuring a setup. Default body text targets this reader.
- **Student** — graduate student new to radiative transfer. Physics derivations and primers live in collapsible `callout-note` blocks they can expand.
- **Contributor** — developer extending climt. Implementation/engineering decisions live in `callout-tip` blocks.

Common pitfalls go in `callout-warning` blocks.

## Site Structure

Quarto project root at `docs/`. Top-level navigation:

1. **Get Started** — install, quickstart, first model. Migrated from `installation.rst`, `quickstart.rst`.
2. **User Guide** — components, initialisation, configuration, memory management, naming, plug-and-play architecture. Migrated from existing RST; `PLUG_AND_PLAY_ARCHITECTURE.md` becomes a User Guide chapter.
3. **Radiative Transfer Walkthrough** — graduate-level textbook absorbed from phase4 plan Part F (tasks 16–25):
   - Ch 1 Why non-grey?
   - Ch 2 Line-by-line physics
   - Ch 3 The k-distribution
   - Ch 4 Correlated-k
   - Ch 5 Gas overlap: additive vs ESFT
   - Ch 6 The cork model
   - Ch 7 The two-stream solver
   - Ch 8 Switching planets
   - Appendix: Performance
   Each chapter combines theory, derivation, climt-source excerpts (via Quarto `include`), and figures built by `_generate_figures.py` (uses `linepyline` for LBL spectra and `climt` for downsampled comparisons).
4. **Experiments** — long-form research case studies, structured as a formal blog (see *Experiments format* below). The cork CO₂-band-refinement saga is the first post, drawing from the existing experiment log in `docs/superpowers/plans/2026-05-16-cork-co2-band-refinement.md`.
5. **API Reference** — auto-generated from docstrings via [`quartodoc`](https://machow.github.io/quartodoc/). Replaces Sphinx autodoc.
6. **Contributing** — dev workflow, how to add an experiment writeup, how to add an RT-walkthrough chapter.
7. **References** — bibliography of cited papers. Every entry is an external link to the publisher / DOI / arXiv page. No PDFs in the repo. Existing PDFs under `docs/` (Pincus 2019, Louis 79, Emanuel 1991/1999, cork series, etc.) are deleted as part of the migration; their citations move to References with `url=` fields in the BibTeX file.

Notebooks (`k_distribution_demo`, `spectral_radiation_anatomy`, `cork_vs_rrtmg` — from phase4 Part E tasks 13–15) are **not** a top-level section. Each lives inside the chapter or experiment that motivates it, rendered as a "Try it yourself" Quarto include at the end. The raw `.ipynb` is downloadable from the page.

## Experiments format

A formal blog, not a rigid template. Each writeup is a single `.qmd` essay; structure is per-topic. What stays consistent across posts is *style*:

- Path: `docs/experiments/<YYYY-MM-DD-slug>/index.qmd`
- Frontmatter metadata (title, author, date, planet, components, tags) drives the Experiments index page — a Quarto listing with post cards, tag filtering, and an RSS feed.
- Code excerpts are pulled from live source files via Quarto `include` rather than retyped, so they cannot drift from the actual scripts.
- Figures and transcripts are static files under `_artifacts/`, regenerated by `make experiments` (see *Artifact regeneration*).
- Layered audience via callouts (`callout-note` for physics, `callout-tip` for engineering, `callout-warning` for pitfalls).
- Citations are `@key` references resolved against a single `references.bib` at the site root; every entry has a `url=` pointing to the canonical paper page.

The cork post becomes the first worked example of the format; future experiments inherit only its conventions, not its skeleton.

## Artifact regeneration

Each experiment and each RT-walkthrough chapter owns a directory containing an `index.qmd`, an `_artifacts/` subdirectory, and a `sources.yml` manifest:

```
docs/experiments/2026-05-18-cork-co2-bands/
  index.qmd
  _artifacts/
    cool_to_space.png
    cool_to_space.txt          # captured stdout
    opacity_structure.png
    ...
    .hashes.json
  sources.yml
```

`sources.yml` declaratively maps each artifact to (a) the command that produces it and (b) the source files whose content determines its validity:

```yaml
artifacts:
  - out: _artifacts/cool_to_space.png
    out_txt: _artifacts/cool_to_space.txt
    cmd: conda run -n climt python examples/cooling_to_space_gsplit_sweep.py
    deps:
      - examples/cooling_to_space_gsplit_sweep.py
      - climt/_components/cork/**/*.py
      - climt/_data/cork/correlated_k/earth_low_res_lw_8gpt.nc
```

A small Python driver `scripts/build_experiments.py` walks `docs/**/sources.yml`, content-hashes the listed deps (glob-expanded), compares to `.hashes.json`, and re-runs only stale artifacts. Captured stdout goes to `out_txt`; the produced figure is copied to `out`. Hashes (not mtimes) so that branch switches and network filesystems don't trigger spurious rebuilds.

`make experiments` invokes the driver. Author workflow: edit script → `make experiments` → `git add` regenerated artifacts + modified script → commit together. CI runs `python scripts/build_experiments.py --check` (no execution, just hash bookkeeping verification) and fails the docs build if any artifact's stored hash is stale.

## Deployment

Single GH Actions workflow at `.github/workflows/docs.yml`.

**Triggers:**
- `push` to `develop` and `main` → builds and publishes
- `pull_request` to either → builds only, uploads rendered site as workflow artifact for PR preview
- `workflow_dispatch` → manual

**Job:** ubuntu-latest, single job.

1. Checkout
2. Set up Python 3.11
3. Install Quarto via `quarto-dev/quarto-actions/setup`
4. `pip install quartodoc` plus minimal climt deps; `pip install -e . --no-deps` so climt is importable (heavy: requires Cython build to succeed; accepted trade-off — alternative of committing pre-rendered API rots silently)
5. `python scripts/build_experiments.py --check` — fail if any artifact is stale
6. `quartodoc build` — regenerate API reference `.qmd`
7. `quarto render docs/` — build site to `docs/_site/`
8. Upload `docs/_site/` as workflow artifact (always)
9. On `push` only: deploy via `peaceiris/actions-gh-pages@v4` to the `gh-pages` branch

**Hosting:** GH Pages on `climt/climt`, source = `gh-pages` branch. URLs:
- `develop` → `https://climt.github.io/climt/dev/`
- `main` → `https://climt.github.io/climt/` (default landing)

Standard `peaceiris` two-version pattern (`destination_dir: dev` for `develop`, root for `main`). Readers land on the released version; the nav footer surfaces a "dev" link.

**Local preview:** `quarto preview docs/` — live-reload dev server on `:4200`. Documented in Contributing.

**Failure surface:**
- `quartodoc` can't import climt → fail fast with a clear message; do not produce partial docs.
- `build_experiments.py --check` finds a stale hash → fail with the artifact name and the dep that changed, instructing the author to run `make experiments` locally and commit.

## Deferred: in-browser executable code

Pyodide-powered live code cells (via Quarto's `quarto-live` / `quarto-pyodide` extension) are **deferred**, not included in v1.

**Rationale.** Live cells require a pure-Python climt wheel loadable in Pyodide. That wheel is the goal of [Phase 2 of the release plan](../release-plan-phase1-numba-phase2-pyodide.md). Coupling the website spec to Phase 2 would (a) block the website ship on Phase 2 completion, (b) force every chapter author to track which components are Pyodide-safe, a moving target until Phase 2 settles, (c) create an implicit cross-plan contract that's easy to violate silently (a `scipy` import slipping into a component would break live cells in production without any obvious failure signal).

**Decision (option A from brainstorming).** Hard sequencing. Website v1 is Pyodide-agnostic — static artifacts everywhere. After both this spec and Phase 2 have shipped, a small follow-up spec (`<date>-climt-website-live-cells-design.md`) wires Pyodide into the existing chapters where it materially helps (Ch 3 k-distribution slider, Parmentier playground in Ch 6, the three pedagogical notebooks).

**Cross-references.** When the implementation plans are written:
- This website plan's "Follow-ups" section links to the live-cells follow-up spec and identifies the pyodide release plan as its blocker.
- The pyodide release plan gets a forward link to the live-cells follow-up, identifying the website plan as its upstream.

The bidirectional link makes the dependency explicit without entangling the two specs.

## Migration

Single migration PR off `develop`:

1. Add Quarto config (`_quarto.yml`, `references.bib`, theme, navigation).
2. `pandoc`-convert every `.rst` under `docs/` to `.qmd`; hand-tidy directives Quarto doesn't understand (autodoc → quartodoc YAML, toctree → `_quarto.yml` navigation).
3. Convert the existing notebooks (`Description_of_SecondBEST.ipynb`, `Implicit_Scheme_Derivation.ipynb`) into chapter `.qmd` files with embedded outputs.
4. Delete all `*.pdf` under `docs/`; migrate their citations to `references.bib` with `url=` fields.
5. Delete superseded Sphinx machinery: `conf.py`, `Makefile`, `make.bat`, `modules.rst`, every `.rst` whose content is now in a `.qmd`.
6. Scaffold the RT walkthrough directory with empty chapter `.qmd` files and the `_generate_figures.py` script.
7. Author the cork experiment post end-to-end, including `sources.yml` and the regenerated artifacts.
8. Add `scripts/build_experiments.py`, the `Makefile` target, and `sources.yml` for each chapter and experiment that has artifacts.
9. Add `.github/workflows/docs.yml`.
10. Enable GH Pages in the repository settings (one-time, manual).

Subsequent PRs fill the empty RT chapters and add new experiment posts.

## Out of scope

- Pyodide-powered live code cells (deferred — see *Deferred*).
- Site search beyond Quarto's built-in client-side search.
- Internationalisation / translations.
- Versioned API docs for old climt releases (only `develop` and `main` are published).
- Replacing existing CI workflows beyond the docs job.

## Open questions resolved during brainstorming

| Question | Decision |
|---|---|
| Relationship to existing Sphinx docs | Replace with one unified site |
| Generator | Quarto |
| Initial experiment content | Cork saga, end-to-end |
| Reader | All three (student / user / contributor), layered via callouts |
| Code execution model | Static artifacts, regenerated locally via `make experiments` |
| Artifact flow | `make experiments` recipe, author runs locally and commits |
| Hosting | `climt.github.io/climt` via project Pages, two-version (dev / main) |
| References / PDFs | External links only; no PDFs in repo |
| Notebooks placement | Inside motivating chapter / experiment, not top-level |
| Writeup structure | Formal blog (no rigid template), shared style only |
| Pyodide live cells | Deferred (option A) — bidirectional links between plans |

## Success criteria

1. `https://climt.github.io/climt/` serves the rendered site after the first merge to `main`.
2. The cork post is published and readable end-to-end by a student who has not been part of the development sessions.
3. All eight RT walkthrough chapters render with at least their theory text and figure placeholders (filling figures is a follow-up).
4. `make experiments` and `python scripts/build_experiments.py --check` work locally and in CI; a deliberately-stalled artifact fails CI.
5. The existing `docs/*.rst` and `docs/*.pdf` files are deleted; their content is either migrated or, for the PDFs, referenced by external link.
6. `quartodoc` generates an API reference that covers at least the same surface as the current Sphinx autodoc.
